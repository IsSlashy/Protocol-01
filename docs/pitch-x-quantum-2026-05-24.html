02 Crypto-agility framework

We separate the transport from the lock.

Crypto-agility isn’t a feature you bolt on — it’s an architectural choice. We split the wallet stack into two independently-swappable layers.

LAYER 1 · SWAPPABLE

Transport signature

Today: Ed25519 (Solana protocol-level).
Tomorrow: Dilithium / Falcon when validators migrate.
Bridge: ephemeral submitter — single-slot key, thrown away.

LAYER 2 · POST-QUANTUM

Spend authorization

STARK over Goldilocks + Poseidon hashes.
Zero elliptic curves in the auth path.
Shor-immune by design — Grover only halves hash security.

RESULT

Funds stay safe

Even if Ed25519 falls. Even if validators haven’t migrated yet. No fork, no migration, no asset risk — each layer rotates on its own schedule.

03 The solution

Three guarantees. Live on devnet today.

Invisible to the merchant

The merchant verifies a STARK proof, never a signature. They learn one fact: this subscription is valid for this period. Not your wallet. Not your identity.

Useless to the hacker

The merchant DB stores only 32-byte commitments. No card. No email. No address. A breach leaks meaningless hashes. Nothing to sell.

Quantum-safe today

Authentication uses STARK over Goldilocks + Poseidon. Zero elliptic curves in the auth path. Shor cannot touch it. Grover only halves hash security. (This line used to claim 128-bit PQ effective; that is the hash, not the proof. The measured classical proof soundness is 42-52 bits per circuit, so the quantum figure is ~21-26.)

Q1 Competitive
How is this different from Umbra?

Umbra uses Groth16 over BN254 for anonymity, plus Arcium MPC for confidential arithmetic. Both have weaknesses we don’t share:

Umbra weaknesses

  • Groth16/BN254 — elliptic-curve, Shor-breakable
  • Trusted setup ceremony — toxic waste risk
  • Arcium MPC — committee trust assumption

Protocol 01

  • STARK — transparent, no trusted setup
  • Hash-based — post-quantum sound
  • Zero committee — only Solana validators

Same family in spirit. Different security model. AMD vs Nvidia — we’re the leaner, Solana-native alternative.

Q2 Cryptographic
What stops merchants from colluding to deanonymize users?

The STARK proof reveals one fact only: “the holder of commitment X has a valid subscription with merchant M at period P.”

  • If all merchants pool their data, they see N distinct commitments per user — each is unlinkable to a wallet, IP, or each other.
  • The denominated pool guarantees the anonymity set: if 100 people deposit 0.1 SOL, your commitment is indistinguishable from 99 others.
  • For maximum unlinkability: one commitment per service — HKDF-derived from your spending key. Even colluding merchants cannot correlate across services.

Q4 Cryptographic
Why STARK and not Groth16 or PLONK?
  • No trusted setup — STARK is transparent. Groth16 needs a per-circuit ceremony. PLONK needs a universal SRS. Both are operational risks at scale.
  • Post-quantum sound — STARK security reduces to hash collision resistance (Grover-bounded) and FRI (information-theoretic). No elliptic curves. Shor doesn’t apply.
  • Faster prover for our circuit sizes (~10K–100K constraints) — Winterfell on Goldilocks beats snarkjs Groth16 by 3–5x on mobile.
  • Trade-off: larger proofs (145KB vs 256B for Groth16). We rent a buffer account — ~0.001 SOL per subscribe. Still cheaper than Stripe’s $0.30 flat fee.
Q5 Integration
How does a merchant integrate this?

Three lines of TypeScript, via the @protocol01/specter-sdk:

// On every authenticated API call:
import { verifySubscription } from '@protocol01/specter-sdk';
const valid = await verifySubscription(commitment, 'disney-plus');
if (!valid) return res.status(402).json({ error: 'subscription required' });

The SDK fetches the vault from on-chain, validates the period, returns true/false. No key management. No PII to store. No PCI compliance. No GDPR exposure.

For session tokens (NordVPN pattern): issueAccessToken(commitment, ttl) returns a short-lived JWT signed by the merchant’s own key, scoped to the verified commitment.

Q6 Product
What if the user loses their device?

Subscriptions are account-scoped, not device-scoped:

  • The subscriber commitment derives from a spending key, stored encrypted (SecureStore + PBKDF2 600K rounds).
  • New device with same seed phrase — same key — same commitment — subscriptions auto-recover.
  • Lost the seed? Cross-device recovery flow: scan your on-chain vault PDAs, prove ownership with a fresh STARK proof bound to the new seed, refund routes to a new commitment.

Same UX as recovering a Solana wallet today — the seed is the source of truth.

Q7 Regulatory
What about KYC and compliance?

Privacy is not the same as untraceability. Our architecture supports optional zk-attestation layers:

  • A merchant can require: “prove you’re not on OFAC” via zk-attestation (zkPass, Reclaim).
  • A merchant can require: “prove you’re over 18 in a permitted jurisdiction.”
  • These attach as extra public inputs in the STARK proof. Merchant verifies them alongside ownership.

The user proves the attestation without revealing identity or document. We don’t replace KYC providers — we let merchants accept their proofs privately.

Today’s demo doesn’t ship this — it’s optional SDK integration.

Q9 Architecture
If the relayer goes down, does the system break?

No. Two layers of redundancy:

  • Direct on-chain fallback — if the relayer errors, the mobile client submits directly. User pays gas, privacy degrades by one fact (tx fee payer visible), subscription still works.
  • Multi-relayer rotation (shipped Sprint 3) — client picks from on-chain registry, filters by last_active_slot, auto-rotates on failure. No central worker.

The relayer is a privacy enhancement, not a critical path. The core STARK auth runs entirely on Solana validators.
