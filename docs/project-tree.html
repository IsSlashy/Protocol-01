Protects against quantum attacks on Ed25519 signing. Ed25519 is still used (Solana platform requirement) but is NOT the security boundary — SHA-256 preimage is.

32 hash chains, w=16, SHA-256. One-time signature that rotates the public key after each withdrawal. ~100-150K CU. Quantum-secure because security reduces to hash preimage resistance.

2-phase TX authorization. Commitment posted on-chain first → reveal within slot window. Prevents quantum front-running of transactions.

▶ TX transfer.circom — 2-in-2-out shielded transfer (Zcash-style) ~12K constraints

Transfer Circuit ~12,222 constraints

Proves a valid 2-input 2-output shielded transfer. The most complex Circom circuit in the project.

Public Inputs

  • merkle_root — Current pool root
  • nullifier_1, nullifier_2 — Spent note nullifiers
  • output_commitment_1, output_commitment_2 — New note commitments
  • public_amount — Fee (0 for private-only)
  • token_mint — Token identifier

Private Inputs

  • spending_key — Owner's secret key
  • in_amount_1/2, in_rand_1/2 — Input note values
  • out_amount_1/2, out_rand_1/2, out_recipient_1/2 — Output notes
  • path_elements, path_indices — Merkle proofs for both inputs

Components

Poseidon (hash), MerkleTreeChecker(15), Num2Bits(64) for range proofs

What It Proves

Sender owns both input notes (via spending_key) → input notes exist in Merkle tree → output commitments are well-formed → input sum = output sum + public_amount (conservation) → nullifiers are deterministic (prevent double-spend).
▶ CB confidential_balance.circom — Hidden balance updates (deposit/withdraw/send/receive) ~1,382 constraints

Confidential Balance Circuit ~1,382 constraints

Proves a valid balance state transition without revealing amounts. Used by zkSPL.

Public Inputs

  • old_commitment, new_commitment — Balance commitments
  • amount_hash — Poseidon(amount, amount_salt)
  • public_credit, public_debit — Deposit/withdrawal amounts
  • token_mint, nonce

Private Inputs

  • old_balance, old_salt, new_balance, new_salt
  • amount, amount_salt, spending_key, is_debit

Key Constraint: Conservation Law

old_balance + private_credit + public_credit = new_balance + private_debit + public_debit
Also enforces: public_credit * public_debit === 0 (no simultaneous deposit+withdraw)
▶ BP balance_proof.circom — Prove balance ≥ threshold without revealing amount ~644 constraints

Balance Proof Circuit ~644 constraints

Proves "I have at least X tokens" without revealing the actual balance. Uses 64-bit range checks to ensure (balance - threshold) is non-negative.

Public Inputs

  • balance_commitment, threshold, token_mint

Private Inputs

  • balance, salt, nonce, spending_key

How It Works

Compute owner = Poseidon(spending_key) → verify commitment = Poseidon(balance, salt, nonce, owner, token_mint) → compute difference = balance - threshold → range-check difference to 64 bits (if negative, wraps to huge number, fails check).

Denominated Pool Circuit ~4,273 constraints

Fixed-denomination anonymous withdrawal. All deposits are the same amount, so withdrawals are perfectly unlinkable.

▶ S stark/ — 6 STARK AIRs (Winterfell, quantum-resistant, no trusted setup) Post-Quantum

STARK Proof System

Quantum-resistant proof system based on Winterfell v0.10. Uses Goldilocks field (p = 2^64 - 2^32 + 1), Poseidon hash with full S-box (x^7, 30 rounds), Blake3 Merkle trees. Compact proofs (~9KB). No trusted setup required (unlike Groth16).

Why STARK? Groth16 uses BN254 elliptic curve pairing, which is vulnerable to Shor's algorithm on quantum computers. STARKs are hash-based — security reduces to collision resistance of hash functions, which is quantum-resistant.
