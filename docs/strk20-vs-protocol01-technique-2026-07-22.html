Trois constats issus du code, chacun invalidant une hypothèse de la roadmap du buildathon.

Constat 1

STRK20 est open source

github.com/starkware-libs/starknet-privacy — Apache 2.0, ouvert le 8 juillet 2026. Contient le contrat Cairo du pool, le service de discovery en Rust, le SDK TypeScript, les preuves formelles Lean 4 et les contrats anonymizer. Pool mainnet déployé à 0x040337b1af3c663e86e333bab5a4b28da8d4652a15a69beee2b677776ffe812a.

Le risque « SDK gated » du plan initial n'existe plus. Ce qui est réellement gated : l'URL du proving service, celle de l'indexer (variables d'environnement sans valeur par défaut publiée nulle part), l'adresse du pool Sepolia, et le paquet npm qui vit sur GitHub Packages, pas sur npm public.

Constat 2

Le projet prévu ne peut pas marcher

Le plan était : Specter dérive une adresse furtive, STRK20 transfère en privé vers elle. Impossible. Il n'existe aucune adresse furtive dans STRK20, et le destinataire doit être un compte Starknet déployé et enregistré avec une clé de vue publique on-chain.

Leur contournement documenté est un contrat d'escrow avec lien de claim off-chain, pas de la découverte de destinataire. Le point de branchement doit bouger — voir section 5.

Constat 3

Le vrai trou est meilleur que celui prévu

À l'enregistrement, le contrat chiffre lui-même la clé de vue privée de l'utilisateur vers la clé publique de l'auditeur, et la stocke on-chain de façon immuable.

Une clé qui déchiffre l'historique bidirectionnel complet d'un utilisateur, chiffrée par ECDH sur la courbe STARK, publiée on-chain, immuable (WriteOnce), permanente. C'est la surface harvest-now-decrypt-later la plus dense du système. La Q3 du brief visait juste ; le code la confirme mot pour mot.

STRK20 · LE MODÈLE

La surprise architecturale principale : elle inverse l'intuition de quiconque vient de Tornado, Zcash, ou de tes propres pools dénommés.

Il n'y a pas d'arbre de Merkle

Pas d'accumulateur, pas de racine, pas de fenêtre de racines historiques. Un grep -ril merkle sur tout le dépôt ne renvoie qu'un seul fichier, et le hit parle du trie d'état de Juno, pas du protocole. Les notes vivent directement dans des maps de stockage Cairo.

notes: Map<felt252, Note>, nullifiers: Map<felt252, bool>, recipient_channels: Map<ContractAddress, Vec<EncChannelInfo>>,
packages/privacy/src/privacy.cairo:88-99

Une note n'est pas un hash-commitment

pub struct Note { /// The packed value of the note `(salt, amount)` pub packed_value: felt252, /// The token address of the note (zero for encrypted notes). pub token: ContractAddress, }
packages/privacy/src/objects.cairo:89-100

Le propriétaire, le token et l'index ne sont pas dans un préimage de commitment : ils sont liés implicitement par la clé de stockage.

note_id = Poseidon(NOTE_ID_TAG, channel_key, token, index, 0) nullifier = Poseidon(NULLIFIER_TAG, channel_key, token, index, 0, owner_private_key)
packages/privacy/src/hashes.cairo:200-236

La conséquence à retenir

Comme channel_key est un secret partagé uniquement entre l'émetteur et le destinataire, les slots de stockage sont pseudo-aléatoires pour tout observateur. Le pseudo-aléatoire de l'adresse de stockage remplace l'anonymat d'ensemble d'un arbre de Merkle. C'est une hypothèse de sécurité différente, et c'est exactement là que l'argument post-quantique mord le plus fort.

Dépenser : lecture de stockage, pas preuve d'appartenance

let subchannel_marker = compute_subchannel_marker(...); assert(self.subchannel_exists.read(subchannel_marker), errors::SUBCHANNEL_NOT_FOUND); let packed_value = self.notes.entry(note_id).packed_value.read(); assert(packed_value.is_non_zero(), errors::NOTE_NOT_FOUND);
packages/privacy/src/privacy.cairo:585-629

Asymétrie du nullifier — un point où ils sont devant

Le nullifier contient la clé privée du propriétaire. L'émetteur d'une note ne peut donc pas calculer son nullifier, et ne peut pas observer quand son paiement est dépensé. Protocol 01 n'a pas cette propriété.

STRK20 · LE CHIFFREMENT

Pas de KEM au sens moderne, pas de chiffrement symétrique authentifié. Deux couches : ECDH sur la courbe STARK, puis masquage additif.

Couche 1 — ouverture de canal (asymétrique)

ECDH sur la courbe STARK avec un scalaire éphémère r par canal. Seule l'abscisse du point est utilisée. La KDF est un simple Poseidon domain-séparé, et le « chiffrement » est une addition dans le corps de base.

fn _compute_shared_x(ephemeral_secret: felt252, public_key: felt252) -> (felt252, felt252) { let ephemeral_pub_point = GEN_P().mul(scalar: ephemeral_secret); let public_point = EcPointTrait::new_from_x(x: public_key)...; let shared_point = public_point.mul(scalar: ephemeral_secret); let shared_x = ...x(); }
packages/privacy/src/utils.cairo:123-145
enc_channel_key = h(CHANNEL_KEY_TAG, rK.x) + channel_key enc_sender_addr = h(SENDER_ADDR_TAG, rK.x) + sender_addr

Couche 2 — données dans le canal (symétrique)

enc_amount = (Poseidon(ENC_AMOUNT_TAG, channel_key, token, index, 0, salt) + amount) mod 2^128 enc_token = Poseidon(ENC_TOKEN_TAG, channel_key, index, 0, salt) + token packed_value = salt * 2^128 + enc_amount // salt 120 bits, choisi par l'émetteur
packages/privacy/src/hashes.cairo:212-222

Dérivation de la clé de canal

channel_key = Poseidon(CHANNEL_KEY_TAG, sender_addr, sender_private_key, recipient_addr, recipient_public_key)

Les canaux sont strictement directionnels : Alice→Bob et Bob→Alice sont deux canaux distincts. Un dépôt est un canal de soi vers soi.

Contrainte de clé canonique

Comme seules les abscisses servent à l'ECDH, k et ORDER−k seraient indistinguables. Le contrat impose donc is_canonical_key(key) = key < HALF_ORDER. Une clé hors borne compile mais dérive silencieusement de mauvaises clés de canal : les notes ne se déchiffrent jamais.

Le schéma est figé dans le contrat

Aucun champ de version ou d'algorithme sur Note ni sur EncChannelInfo. Le seul versionnage est le suffixe :V1 dans les 17 tags Poseidon. Changer de schéma exige un upgrade de contrat via ReplaceabilityComponent. Réponse à la Q2 : non, pas extensible.

Audit OpenZeppelin — le r éphémère

Le scalaire éphémère est fourni par le client et seulement validé non nul. Le contrat « n'impose pas l'unicité ni n'empêche la réutilisation de r », d'où un risque de réutilisation déterministe de ciphertext. Second constat : une auditor_public_key invalide déclenche des panics EcPointTrait::new_from_x(...).unwrap() capables de bloquer enregistrements et retraits à l'échelle du système. Commit audité c5e2fb53…

STRK20 · ADRESSAGE DU DESTINATAIRE

Réponse à la question n°1 du brief. Elle est nette, et elle est structurante.

Il n'y a ni tag de détection, ni view tag, ni scan de tout le pool. Le contrat stocke un seau par destinataire, indexé par son adresse Starknet en clair.

/// Map of recipient_addr to a list of their encrypted channels. recipient_channels: Map<ContractAddress, Vec<EncChannelInfo>>,
packages/privacy/src/privacy.cairo:88-89

L'émetteur ajoute un EncChannelInfo dans le seau du destinataire via l'action serveur Append. Le destinataire ne lit que son propre seau et déchiffre par essai chaque entrée.

La fuite qui en découle

Le slot de stockage est dérivé déterministiquement de l'adresse en clair via get_storage_var_address("recipient_channels", [recipient_address]). Tout observateur des state diffs voit donc qu'une adresse précise vient de recevoir un nouveau canal.

Seul le premier transfert d'une paire (émetteur, destinataire) fait cela ; les notes suivantes vont dans des slots dérivés du channel_key secret. Le SDK émet d'ailleurs un warning WarningCode.USER_LINKAGE quand plusieurs OpenChannel apparaissent dans une même transaction. Leurs propres docs listent la « channel-open linkability » comme limite connue.

La discovery : balayage d'index dense à 3 niveaux

NiveauOpération
1Lire son propre recipient_channels et déchiffrer par essai ECDH chaque entrée
2Parcourir les index de sous-canal 0, 1, 2… par canal, en démasquant le token
3Parcourir les index de note 0, 1, 2… par (canal, token), démasquer les montants, tester chaque nullifier dérivé contre l'état on-chain

Le balayage s'arrête au premier slot vide. Tous les slots sont WriteOnce et les index doivent être séquentiels (INDEX_NOT_SEQUENTIAL) : c'est la densité qui garantit la terminaison.

Le point où ils sont architecturalement devant

Le coût de scan est proportionnel à ton activité, pas au volume du pool. « A pool with millions of transfers costs you no more to scan than a quiet one. » La discovery est en outre une lecture gratuite : pas de preuve, pas de frais, pas de soumission. Les notes ne sont dépensables que 10 blocs après création.

Ce qui reste public à chaque bord

L'événement Deposit porte user_addr, token, amount en clair. Withdrawal porte to_addr, token, amount en clair plus un enc_user_addr chiffré pour l'auditeur. ViewingKeySet lie publiquement une adresse à sa clé de vue publique. Leurs docs le résument ainsi : « edges are public by design ».

La conservation de la valeur n'est pas une contrainte de circuit

C'est un registre de balance temporaire par token, à l'intérieur d'une transaction. Deposit et UseNote ajoutent, CreateNote et Withdraw retranchent. La balance ne peut jamais devenir négative, et chaque token doit finir exactement à zéro.

STRK20 · OÙ LA PREUVE EST VÉRIFIÉE

Le chemin exact, souvent mal décrit. C'est l'axe où l'écart architectural avec Protocol 01 est le plus grand.

#Étape
1Le SDK compile les actions et les envoie à un proving service opéré par un tiers
2Le service exécute dans un bloc Starknet virtuel (Virtual SNOS), un OS modifié à fonctionnalité réduite. Les builtins add_mod, mul_mod et Keccak sont exclus des claims prouvés en phase 1
3La preuve Stwo voyage dans les champs optionnels proof (uint32[]) et proof_facts (felt252[]) d'une Invoke V3 — pas dans le calldata
4Un vérificateur S-two en Rust embarqué dans le gateway / séquenceur vérifie. Pas un contrat Cairo. Pas de récursion dans la preuve d'état L2 en phase 1
5Le contrat de pool lit seulement les petits proof_facts via un syscall dédié, et valide la variante de programme, le bloc de base, la fenêtre de validité et le hash de message
SNIP-36 — community.starknet.io/t/snip-36-in-protocol-proof-verification/116123

Deux aveux qu'ils écrivent noir sur blanc

« applications built with this feature will have degraded security compared to native Starknet applications » — à corriger dans une release ultérieure.
« The protocol is not zero-knowledge by default ; proofs reveal no execution data beyond declared public input. »

En phase 1 les preuves sont vérifiées par le consensus mais pas par le SNOS, ne sont pas dans les blocs, ne sont pas récupérables au feeder gateway, et ne sont conservées que quelques semaines. Les full nodes ne re-vérifient pas. La confidentialité v0.14.2 est décrite comme « de facto », le vrai ZK est reporté en phase 2.

Pourquoi SNIP-36 existe — et pourquoi c'est ton meilleur angle

« Including the full proof (often tens of thousands of felts) in calldata exceeds the present transaction limit (5K felts). »

La vérification dans un contrat Cairo a bien été tentée — Integrity, de Herodotus, déployé sur Starknet — et a dû être découpée en plusieurs contrats et plusieurs transactions à cause des limites de classhash, de calldata et de pas Cairo (3M pas par transaction). Autrement dit : ils ont rencontré exactement ton problème, et l'ont résolu en changeant le protocole de la L2 plutôt qu'en optimisant le vérificateur. Cette option ne t'est pas offerte sur Solana.

Fenêtre de validité de preuve — leur analogue de tes racines historiques

Le contrat rejette les preuves plus vieilles que proof_validity_blocks (450 blocs, ~15 min à 2 s/bloc). Convention du SDK : prouver à currentBlock - 10. Tout état on-chain lu par la preuve (clé de vue du compte, balance du déposant, set de nullifiers) doit avoir été écrit au moins 10 blocs avant le bloc de base. Ce n'est pas le même mécanisme que le tien : le tien résout la concurrence sur l'état de l'arbre, le leur la fraîcheur de l'exécution virtuelle.

STRK20 · LE SYSTÈME DE PREUVE

Stwo, Circle STARK sur M31. Et le point architectural qui explique tout le reste : Cairo est une AIR de CPU fixe.

Le corps : M31, p = 231 − 1

Tour M31 → CM31 (ext. quadratique) → QM31 (ext. quartique, utilisée pour Fiat-Shamir et les aléas DEEP/FRI).

Pourquoi pas un corps 64 bits

M31 a une 2-adicité de 1 (p−1 = 2·(230−1)) : aucun sous-groupe lisse en 2k pour une FFT radix-2.

Le Circle STARK contourne ça via la courbe circulaire x² + y² = 1, dont le groupe de points a un ordre de p+1 = 231, exactement une puissance de deux. La CFFT garde la même structure de papillon radix-2, sur des polynômes bivariés restreints au cercle. Papier : Haböck, Levit, Papini, ePrint 2024/278, annonçant 1,4× de gain sur un STARK BabyBear.

Le vrai argument est la densité SIMD : la réduction mod 231−1 est un décalage cyclique, pas une division, et l'arithmétique tient dans des lanes 32 bits AVX2 / AVX-512 / NEON / WASM-SIMD.

Hash de commitment
Blake2s-256 par défaut ; Poseidon252 en option pour règlement Ethereum
Arbre de Merkle
« lifté » : le hash d'un nœud dépend des enfants et des colonnes injectées à cette couche — colonnes de hauteurs différentes sans padding
Paramètres par défaut
log_blowup = 1 (blowup 2), 70 requêtes, 26 bits de grinding, plus un PoW de phase d'interaction
Soundness cible
96 bits conjecturés (régime list-decoding), pas prouvés sous borne de Johnson
Trusted setup
aucun — « fully transparent, no toxic waste, no MPC ceremony »

Le point architectural décisif

Cairo est une AIR de CPU fixe. Un unique jeu immuable de contraintes polynomiales prouve l'exécution valide de la machine Cairo ; le programme applicatif n'est pas compilé en contraintes, il est de la donnée placée en mémoire publique et consommée comme trace.

« We describe a single set of polynomial equations for the statement that the execution of a program on this architecture is valid. Given a statement one wishes to prove, Cairo allows writing a program that describes that statement, instead of writing a set of polynomial equations. » — Cairo paper, ePrint 2021/1063

En pratique stwo-cairo décompose ça en 69+ composants (un par opcode, un par builtin) reliés par des arguments de lookup LogUp. Les builtins sont des périphériques mappés en mémoire qui remplacent un calcul coûteux dans la VM par un composant d'AIR dédié. C'est ça, « le circuit et le contrat sont le même code » : pas de DSL de circuit, pas d'AIR par application, pas de vérificateur déployé par application.

L'axe où l'écart avec Protocol 01 est maximal, dans les deux sens : ils ont une couche complète, et c'est leur surface la plus exposée.

Clé d'auditeur

Screening de dépôt appliqué on-chain

Depuis v0.14.3, chaque dépôt porte une attestation SNIP-12 DepositorValidation { depositor, issued_at } signée par un screener off-chain dont la clé publique STARK est en stockage. Le pool vérifie l'ECDSA. Expiration 300 s, tolérance de dérive future 60 s.

Faire tourner son propre prover ne contourne pas ça. Divergence non expliquée : les docs nomment « FPI » comme screener, le code appelle l'API d'Elliptic via un proxy GCP elliptic-proxy. Avec en plus des listes opérateur blockOverrideAddresses et additionalBlockedAddresses.

Deux constats de confiance

Ce ne sont pas des accusations : c'est ce que disent leur code et leurs specs. En phase 1 ce sont des choix d'architecture explicites.

La mitigation est OHTTP (basé X25519, relais optionnel), et elle ne couvre que la corrélation d'IP.

STRK20 · SURFACE DÉVELOPPEUR

Privacy Wallet API = Starknet Wallet API v0.10.3, publiée en types TypeScript. Exactement trois méthodes. Aucune ne s'appelle shield, unshield ou claim.

wallet_strk20InvokeTransaction // { actions: STRK20_ACTION[] } -> { transaction_hash } wallet_strk20PrepareInvoke // { actions, simulate? } -> STRK20_CALL_AND_PROOF wallet_strk20Balances // { tokens: Address[] } -> STRK20_BALANCE_ENTRY[]
@starknet-io/types-js@0.10.3 — dist/types/wallet-api/methods.d.ts:135,157,174

Les 4 variantes d'action

deposit (toujours vers soi, pas de champ recipient), withdraw, transfer (accepte le littéral "OPEN" comme montant), invoke.

Pas de scan de notes dans la Wallet API

Une dapp ne lit que des balances agrégées par token. Le scan n'existe que dans le SDK bas niveau (discoverNotes, discoverChannels), qui exige la clé de vue. Délibéré : « A normal dapp should not receive the user's viewing key. »

Le SDK bas niveau — builder fluide

await transfers.build(opts) .with(TOKEN, t => t.inputs(note).transfer({ recipient, amount }).withdraw({ amount })) .surplusTo(self) .execute({ provingBlockId });

Verbes : register, deposit, transfer, withdraw, setup, invoke.

Les dire avant qu'on te les demande, c'est ce qui crédibilise le plus. Liste réelle, établie sur le code.

Le view tag ne filtre rien

checkViewTag calcule le tag depuis le secret hybride, donc il exécute une décapsulation ML-KEM-768 complète plus un scalarmult X25519 avant de pouvoir rejeter.

Le commentaire on-chain qui dit que le tag « évite la décapsulation coûteuse » (state/stealth.rs:134-137, avec un taux de rejet annoncé de 99,6 %) contredit directement l'implémentation cliente scan.ts:124-138.

Travail fait deux fois

Après le passage du view tag, verifyStealthOwnership refait à l'identique le scalarmult, la décapsulation et le HKDF. Rien n'est mémoïsé.

Bande passante non bornée

fetchAnnouncements ignore son intervalle de slots (paramètres _fromSlot, _toSlot) et getProgramAccounts télécharge toutes les annonces de 1220 B jamais créées, puis tronque côté client. Pas de dataSlice, pas de pagination.

Pas de flag de complétude

init_stealth_v2 remplit le ciphertext de zéros et rien n'impose que les deux chunks soient écrits. Un PDA à moitié écrit est indistinguable pour le scanner.

3 transactions non atomiques

tx1 crée le PDA et transfère les fonds, avant l'écriture des chunks. Si un chunk échoue, l'argent est à une adresse furtive dont le ciphertext est incomplet, donc introuvable par le destinataire.

Émetteur identifiable

Le PDA est dérivé de la vraie pubkey de l'émetteur (seeds = ["stealth_v2", sender, stealthAddress]), donc chaque annonce lui est publiquement attribuable, indépendamment du signataire de la transaction.

Dépense non PQ

L'adresse furtive est Ed25519, donc dépensable par une signature classique. La découverte est PQ, la dépense ne l'est pas. Le SDK le documente honnêtement et livre un module WOTS+, mais le vérificateur on-chain qui imposerait la seconde signature n'existe pas.

LE TROU PQ, PRÉCISÉMENT OÙ

Deux formulations à ne pas employer

Le brief dit déjà de ne pas dire « STRK20 n'est pas post-quantique ». La vérification adversariale en a trouvé une deuxième, également fausse et qui te ferait corriger sur place : ne dis pas non plus « la confidentialité est hors périmètre ». STRK20 est leur produit de confidentialité, livré deux mois avant la roadmap.

Formulation vérifiée, à utiliser telle quelle

La roadmap post-quantique de StarkWare du 30 juin couvre le hachage et les commitments : Pedersen remplacé par BLAKE2 sur le state commitment, la dérivation d'adresse de contrat et le hash de config de l'OS, plus la migration des contrats existants et les dépendances Ethereum. Elle ne dit pas comment la couche de chiffrement qu'ils ont déjà livrée dans STRK20 sera migrée : les balances chiffrées, et la clé de vue chiffrée on-chain qu'un auditeur désigné peut déchiffrer. C'est une asymétrie qui mérite une question, pas une accusation. Le système de preuve est basé sur des hashes et tient. La couche de confidentialité a été livrée deux mois avant la roadmap et n'y figure pas.

Les deux cibles concrètes

Cible A — la plus forte

La séquestre de clé de vue (EncPrivateKey)

enc_private_key = h(ENC_PRIVATE_KEY_TAG, rK.x) + private_key
  • ça protège l'historique bidirectionnel entier d'un utilisateur, pas une transaction
  • permanent et immuable par conception : l'exposition ne décroît jamais
  • une seule clé d'auditeur cassée expose tous les utilisateurs à la fois, et désanonymise rétroactivement tout le pool depuis mai 2026
Cible B

L'ouverture de canal (EncChannelInfo)

enc_channel_key = h(CHANNEL_KEY_TAG, rK.x) + channel_key enc_sender_addr = h(SENDER_ADDR_TAG, rK.x) + sender_addr
Chez eux, l'adressage des notes dérive du secret de canal. Casser la courbe ne révèle pas seulement qui a reçu combien, ça révèle où toutes les notes sont stockées. La confidentialité et l'adressage reposent sur la même clé, et cette clé est chiffrée on-chain avec de l'ECDH sur courbe elliptique, pour toujours.

Ce qui les protège déjà, à reconnaître d'emblée

Stwo est basé sur des hashes et survit à Shor — à dire en premier. Blake2s est déjà partiellement déployé, l'AA permet un signer PQ dès aujourd'hui. Et surtout : un chiffrement additif dans un corps premier n'a pas de structure exploitable par Shor en lui-même ; la vulnérabilité est entièrement dans l'ECDH qui produit rK.x. C'est le seul composant qu'un KEM remplace. Le changement est chirurgical — c'est ton meilleur argument.

POINT DE BRANCHEMENT RÉVISÉ

Ce qui tombe

L'architecture cible de la roadmap (émetteur dérive une adresse furtive, STRK20 transfère dessus) ne peut pas être implémentée. Ne pas essayer de la forcer. Ne pas proposer de reconstruire un système de notes non plus — le piège n°4 du brief tient toujours.

Ce qui devient le projet

Remplacer l'ECDH sur courbe STARK par un KEM hybride dans les deux structures chiffrées de STRK20, sans toucher au reste du protocole.

Ce qui rend ça défendable en 12 heures :

  • Le périmètre est exactement deux fonctions. _compute_shared_x produit rK.x, et tout le reste du système consomme un felt252 de matière clé. Si rK.x est remplacé par un secret issu d'une décapsulation ML-KEM réduit dans le corps, rien d'autre ne change : ni la structure des notes, ni les nullifiers, ni la discovery, ni les phases.
  • Le combineur OR-sûr de Specter existe déjà et est testé : HKDF(classic || pq, info = transcript). Il se transpose directement, en substituant Poseidon à SHA-256 pour rester dans leur domaine de hash.
  • L'argument « on ne fait pas de mixer maison, on se branche au-dessus » devient littéralement vrai au niveau de la ligne de code.

Détail qui compte : stockage, pas events

STRK20 ne met aucun payload chiffré dans les events — toute la discovery lit du stockage. Un pq_announcer qui émettrait des events divergerait de leur architecture et se ferait remarquer. Packing : 1088 octets à 31 octets par felt = 36 felts. En stockage plutôt qu'en events, ce qui évite aussi le coût de 5 120 L2gas par felt de données d'event (184 320 L2 gas, soit 4,6 L1-gas-équivalent : pas prohibitif, mais inutile).

Règle de coupe révisée

MVP défendable : un handshake ML-KEM-768 dont le secret partagé est réduit dans le corps STARK, utilisé pour masquer un channel_key selon leur formule exacte h(TAG, secret) + value, avec le ciphertext stocké dans un contrat Cairo sur Sepolia, et une démonstration que l'émetteur et le destinataire dérivent le même channel_key.

Ça prouve la substituabilité au niveau exact où elle compte, sans dépendre du proving service, sans dépendre du screening de dépôt, sans dépendre de l'accès au pool — les trois choses qui peuvent te bloquer et dont aucune n'est sous ton contrôle.

Stretch : un vrai transfert STRK20 entre deux comptes enregistrés, avec côte à côte le canal ouvert par leur ECDH et le même canal ouvert par le KEM. Ne jamais sacrifier la vidéo de secours de 17h30.

Devenues inutiles — déjà répondues par le code

Q6SDK gated ou public → open source Apache 2.0
Q8coût des events Cairo → 5 120 L2gas/felt de données, mais STRK20 n'utilise pas d'events pour les payloads

Les vraies bloquantes — première heure

  1. URL du proving service Sepolia. Aucune valeur publique nulle part ; tous les exemples utilisent process.env.PROVING_SERVICE_URL sans défaut, et la demo tombe sur un mock si non défini. Endpoint hébergé par StarkWare ? Credentials ? Rate limits ?
  2. URL de l'indexer de discovery. Même problème (process.env.INDEXER_URL). Endpoint hébergé, ou faut-il faire tourner le container ?
  3. Adresse du pool sur Sepolia. Le mainnet est publié, Sepolia est confirmé supporté mais l'adresse n'est publiée nulle part — elle est résolue par le wallet à l'exécution.
  4. Accès npm au SDK. @starkware-libs/starknet-privacy-sdk renvoie 404 sur le registre public ; c'est sur GitHub Packages. Token nécessaire, ou install git ?

Les techniques qui valent le détour

  1. Migration du format chiffré. Aucun champ de version sur Note ni EncChannelInfo, et clés de vue WriteOnce. Si vous passez le chiffrement en post-quantique, comment migrent les canaux existants et les clés déjà séquestrées ? La meilleure question du lot : concrète, issue du code, sans réponse documentée.
  2. Qui porte la couche chiffrement dans la roadmap PQ ? Oubli, séquencement, ou chantier ouvert non publié ?
  3. La clé de vue privée en clair vers le prover. Modèle de confiance, attestation TEE prévue, politique de rétention ? À poser sans agressivité : c'est un choix d'architecture explicite en phase 1, pas une négligence.
  4. Auditeur à seuil. Les docs le disent supporté, le contrat stocke un seul felt252. Déployé aujourd'hui ? Porteurs de parts ? Process de requête ?
  5. FPI vs Elliptic. Qui signe, qui fournit la donnée, qui contrôle blockOverrideAddresses ?
  6. Le r éphémère réutilisable. Corrigé dans la classe déployée, ou assumé côté client ?

Entre pairs

  1. M31 contre Goldilocks. Quelles contraintes le choix du corps met-il sur les décompositions en bits et les range checks dans leurs circuits privacy ? Tu as un vrai vécu : tu as différé les range checks sur confidential_balance et transfer précisément parce que la décomposition en bits faisait exploser le budget CU.
